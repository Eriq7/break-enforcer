# 第 7 步：$1 授权实测

> 对应交接文档第零节第 7 步。**先跑完这个，再写主应用。**

## 为什么要有这一步

主应用的核心设计是「失败就压 $43，五天后释放」。这个设计成不成立，取决于两个只能实测的数字：

| 问题 | 谁能回答 |
|---|---|
| void 之后钱多快从银行账户回来 | 只有 Eric 那张 RBC Visa Debit 的发卡行知道。Stripe 保证不了 |
| 授权撑不撑得满 120 小时 | 同上。一般上限 7 天，但发卡行可以提前放 |

顺带还验证了第三件事，是交接文档第七节「坑 1」的正面测试：

**off-session 授权到底压不压得动。** 主应用在 50:25 判罚时，Eric 人不在页面上，压款走的是 off-session。
如果他的银行拒绝 off-session 或者要求 3DS，整套机制会静默失效。这个工具两个实验都走 off-session，专门把这件事测出来。

## 安全边界

- 金额**写死**：实验 1 `$1.00`，实验 2 `$1.25`（CAD，2026-10-25 改，金额不同才能在 RBC App 里分清两笔），在 `server.js` 里是常量，不从环境变量读，避免手滑压出一笔大钱
- 全程只用 `authorization` + `void`，**永远不 capture**，钱不会真的被扣走
- 就算忘了 void，授权一般 7 天自己过期，最坏结果是 $1 多挂几天
- `.env` 被 `.gitignore` 挡住。仓库是 public 的，**live secret key 绝对不能进 git**
- key 由 Eric 自己取自己填。Agent 不读不存

## 怎么跑

### 0. 装依赖

```bash
cd Break_Enforcer/experiments/hold-test
npm install
```

### 1. 先用 test mode 空跑一遍

验证代码没写错，不碰真卡。

```bash
cp .env.example .env
```

去 https://dashboard.stripe.com -> Developers -> API keys，**把右上角切到 Test mode**，取 `sk_test_...` 和 `pk_test_...` 填进 `.env`。然后：

```bash
npm start
```

打开 http://127.0.0.1:4242 ，用假卡 `4242 4242 4242 4242`，任意未来的有效期，任意 CVC。把三步点一遍，看到实验 1 的状态走到 `canceled`、实验 2 停在 `requires_capture`，就说明流程是通的。

test 模式的记录存在 `runs/state.test.json`，跟 live 分开，不会互相污染。

### 2. 换成 live，用真卡跑

把 `.env` 里的两个 key 换成 `sk_live_...` / `pk_live_...`（Dashboard 右上角切回 live），重启：

```bash
npm start
```

页面右上角会变成红色的 **LIVE　真钱真卡**。看到这个再往下做。

| 顺序 | 做什么 | 注意 |
|---|---|---|
| 1 | 存卡 | 用 **RBC Visa Debit**。存完页面会显示 `funding`，必须是 `debit`。显示 `credit` 说明卡拿错了 |
| 2 | 点「压 $1 然后立刻 void」 | 这是实验 1 |
| 3 | 打开 RBC App 盯着 | 看到那笔 $1 pending **出现**，回页面点「银行里看到 pending 了」 |
| 4 | 继续盯 | 看到它**消失**，回页面点「pending 消失了」。这一下算出来的就是核心答案 |
| 5 | 点「压 $1.25 并挂住」。两个实验可以同时开 | 这是实验 2。页面会显示 120 小时的倒计时 |
| 6 | 这五天里偶尔看一眼 RBC App | 如果 pending **提前自己消失了**，立刻回页面点「pending 消失了」，那说明惩罚撑不满 5 天 |
| 7 | 到点后 | 重新 `npm start`，打开页面点「现在 void 掉」 |
| 8 | 最后 | 点「导出结论」，把 `runs/report.live.md` 给下一个 Agent |

**服务器不需要一直开着。** 授权挂在 Stripe 那边，本地进程关掉不影响它。第 7 步隔五天再打开就行。

## 只有 Eric 能做的那部分

脚本看不见银行账户。pending 什么时候出现、什么时候消失，只有 Eric 在 RBC App 里能看见。
所以那两个按钮必须由他在**看到的那一刻**点，时间戳才准。晚点几小时，结论就废了。

## 测出来之后怎么办

`runs/report.live.md` 里自动带了这张决策表，也就是交接文档第零节的原表：

| 测出来 | 怎么办 |
|---|---|
| 放开当天就回来，5 天也压得住 | 直接按现方案做，进第 8 步 |
| 放开要 2 天以上才回来 | 方案还能用，但要告诉 Eric「罚 5 天实际是 7 天」 |
| 放开要一周以上 | 得换思路，重新讨论 |
| 5 天撑不住，提前放了 | 需要在快过期时续压一次，逻辑变复杂但能做 |

额外的一条，这个工具新加的：

| 测出来 | 怎么办 |
|---|---|
| off-session 直接被拒或要求 3DS | 主应用不能指望 50:25 静默压款。要么改成「会话开始时先 hold」（但那个方案第二节已经否决过），要么在判罚失败时挂欠账、还清前不许开新会话（第七节坑 1 的方案） |

## 不在这次范围内

- **$2.25 服务费的真实 capture 没测。** 定价方案 B 的第二笔是真扣款，手续费 2.9% + $0.30。
  逻辑上没有不确定性，不值得为它花掉一次真实扣款，留到主应用联调时一起测
- payout 到账时间没测。Payout schedule 已确认是 Automatic / Daily，打款免费，跟惩罚设计无关
